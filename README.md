### Задание 1

Активный master-сервер и пассивный slave-сервер
Все операции чтения и записи выполняет основной master-сервер. Slave получает копию данных посредством репликации, но в обычной работе почти не используется.
Основные преимущества:
- повышение отказоустойчивости: если master выйдет из строя, slave можно назначить новым основным сервером;
- наличие актуальной резервной копии базы на другом сервере;
- возможность выполнять резервное копирование и технические проверки на реплике, не нагружая основной сервер;
- уменьшение времени простоя при аварии.
Такая схема в первую очередь повышает надёжность системы, но почти не увеличивает её производительность, пока пассивный сервер не обслуживает запросы.
Master-сервер и несколько slave-серверов
Все запросы на изменение данных — INSERT, UPDATE, DELETE — направляются на master. Запросы на чтение — SELECT — можно распределить между несколькими slave-серверами.
Основные преимущества:
- горизонтальное масштабирование операций чтения;
- распределение нагрузки между несколькими серверами;
- увеличение количества пользователей и запросов, которые может обслужить система;
- возможность выделить отдельные реплики для отчётов, аналитики или резервного копирования;
- повышение отказоустойчивости: при поломке одной реплики остаются другие;
- возможность размещать реплики ближе к пользователям в разных регионах.
Главное ограничение такой схемы — возможная задержка репликации. Изменения, записанные на master, могут появиться на slave не мгновенно, поэтому некоторое время реплика способна возвращать устаревшие данные.


### Задание 2

При вертикальном шардинге таблицы разделяются по назначению и размещаются в разных базах данных.
Разделение выполняется следующим образом:
- в базе пользователей хранятся учётные записи и персональные данные;
- в базе каталога хранится информация о книгах;
- в базе магазинов хранятся адреса и сведения о торговых точках.
Связи между таблицами поддерживаются на уровне приложения.
При горизонтальном шардинге одна таблица делится на части по строкам. Каждый шард имеет одинаковую структуру таблицы, но хранит разные записи.
Предлагаемое распределение:
- пользователи распределяются по user_id;
- книги — по book_id;
- магазины — по region_id.
Вертикальный и горизонтальный шардинг можно использовать одновременно: сначала данные разделяются по назначению, а затем каждая база разбивается на несколько горизонтальных шардов.

![alt text](https://github.com/VaRlicH/12-07/blob/main/img/structbd.png)


 Каждый шард представляет собой отдельную группу серверов:
- Primary (master) работает в режиме чтения и записи;
- Replica (slave) работает преимущественно в режиме чтения;
- все INSERT, UPDATE и DELETE направляются на primary;
- обычные SELECT могут распределяться между репликами;
- одна реплика может работать как горячий резерв и стать основной при отказе primary.
Shard Router определяет расположение данных.

Таким образом, вертикальный шардинг разделяет базу по назначению таблиц, а горизонтальный — по строкам внутри каждой таблицы. Репликация дополнительно обеспечивает распределение запросов на чтение и отказоустойчивость.
